## 🛠 작업 규칙 (Working Rules)

원활한 협업과 코드 품질 유지를 위해 아래의 규칙을 준수합니다.

### 1. 커밋 컨벤션 (Commit Convention)

커밋 메시지는 작업 내용을 한눈에 파악할 수 있도록 아래 형식을 따릅니다.

| 타입 | 의미 |
| :--- | :--- |
| **Feat** | 새로운 기능 추가 |
| **Fix** | 버그 수정 |
| **Refactor** | 코드 리팩토링 (기능 변화 없음) |
| **Test** | 테스트 코드 추가 및 리팩토링 |
| **Docs** | 문서 수정 (README 등) |
| **Chore** | 빌드 업무, 패키지 매니저 설정 등 기타 작업 |


### 2. 개발 프로세스 (Workflow)

모든 작업은 아래의 프로세스를 거쳐 메인 코드에 반영됩니다.

1. **Issue 생성**: 작업 시작 전 GitHub Issue를 생성하여 작업 내용을 정의합니다.
2. **Branch 생성**: 이슈 번호를 포함한 기능 브랜치를 생성합니다. (예: `feat/#1-login`)
3. **개발 및 테스트**: 
   - 기능 구현 시 **단위 테스트(Unit Test)** 및 **통합 테스트(Integration Test)**를 필수로 수행합니다.
   - 모든 테스트가 통과된 상태에서만 커밋을 진행합니다.
4. **Pull Request (PR)**: 작업 완료 후 PR을 생성하고 상세 내용을 작성합니다. 이때 리뷰 요청도 진행합니다.

### 3. 코드 리뷰 및 머지 (Review & Merge)

* **알림 발송**: PR 생성 및 리뷰 요청 후에는 즉시 **카카오톡 단톡방**에 메시지를 남겨주세요.
* **리뷰 기한**: 리뷰 요청을 받은 팀원은 **12시간 이내**에 리뷰를 진행하는 것을 원칙으로 합니다.
* **Merge 조건**: 동료의 리뷰를 받고 승인(Approve)이 완료된 후에만 머지할 수 있습니다.
